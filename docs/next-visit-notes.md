# Next-visit Notes

## Purpose and Scope

WORK-ID: MY-TRIPS-RETURN-NOTE. The owner authorized a small retention improvement and production deployment on 2026-10-23. This is an implementation/validation release, not evidence of increased return visits.

The hypothesis is that remembering an unfinished decision (for example, comparing cancellation terms at two hotels) makes the next visit useful. Each city in My trips has one small next-visit note, visible above the last-read guide and preparation list. The editor is collapsed until opened; saved text remains visible. The English and Korean homepages are unchanged, including their rendered HTML. No banner, notification permission, subscription, account or new AI request is added.

## Storage and Editing

- One optional localStorage key per city: `tripcompass.return-note.fukuoka.v1`, `.osaka.v1`, `.tokyo.v1`; each stores `{version: 1, text}`. Text is limited to 240 UTF-16 code units, matching native textarea maxlength. Whitespace at the edges is trimmed on explicit save.
- Both languages show the same user-written note; there is no translation call. Saved notes survive reload and later visits in that browser profile, not another device. A note can be saved before starting preparation.
- Visits do not write. Save note updates only that city; saving an empty note removes only its note key. Preparation, bookmarks, decision-board and reading data are untouched. Resetting a workspace intentionally does not delete its independent note.
- Drafts use separate tab-local sessionStorage keys, `tripcompass.note-draft.<city>.v1`, with `{version: 1, text, base}`. Input events preserve untrimmed text (including intentional blank edits) and the raw saved-note baseline, at most one draft per city. Reload and EN/KO navigation restore the draft and open its editor without stealing focus. Only explicit save writes the durable note. Save/discard clears the draft; failed discard preserves it. Tab/session restoration may retain or copy sessionStorage, so this is not a backup, cross-device synchronization or a promise of deletion on browser close.
- Protected drafts need no departure prompt. Failed draft writes/cleanup retain page state and use a best-effort beforeunload warning; no guarantee is made for abrupt/mobile termination. Invalid snapshots never overwrite saved notes. A saved baseline mismatch prevents overwriting newer notes; a leftover draft after successful save is recognized as obsolete. BFCache return rereads tab state so an already saved/discarded edit does not reappear.
- Clean editors refresh on relevant storage events and BFCache return. Dirty editors retain their draft, reject a save against a changed baseline, and offer Load saved note. When edits or unprotected draft cleanup remain, that action first asks for confirmation in the page language. Cancel, a suppressed dialog or an unavailable dialog preserves the input and draft; confirmation loads the latest saved value only after successful read and draft cleanup. Clean reloads need no dialog. A failed write/delete preserves the draft for retry. Denied or malformed reads disable editing until a successful reload; unreadable records are not overwritten.
- Notes render with textContent/value, not HTML or generated URLs. No data is sent to AI, analytics or `/go`. The editor cautions against entering personal/booking/payment details; privacy documentation explains shared-browser visibility and deletion.

## Saved Note Copying

WORK-ID: SAVED-NOTE-COPY. A user-initiated copy action appears with an available saved city note. It copies only clean saved text, without a city label, URL or other records. Dirty/conflicting editors disable it; missing, malformed or blocked saved notes hide it. The handler checks the current saved baseline before clipboard access, never reads the clipboard and makes no network call. Clipboard denial or an absent API reveals a separate read-only selected field without replacing the editor or draft. Edit/load/storage/BFCache changes clear manual-copy state; late clipboard results cannot restore stale text or steal editor focus. The browser may already have copied a requested snapshot before a concurrent change; the interface does not claim that snapshot is current. No clipboard deletion or cross-device privacy guarantee is made.

Existing preparation, bookmark, note and draft storage writers are unchanged. Old cached markup is tolerated. Unit tests in Phase 2 cover EN/KO across three cities, exact copied text, duplicate/late requests, changed or unreadable records, manual fallback, dirty-draft protection, empty/corrupt data and no persistence writes from copying. Browser release QA uses a mocked clipboard in isolated contexts to avoid replacing the owner's real clipboard, and checks mobile layout and existing record recovery. Production evidence belongs in `docs/CURRENT_STATE.md`; native clipboard behavior on physical devices remains a separate test.

## Follow-up Measurement

Do not add more homepage controls solely because this feature shipped. Ask a few travelers whether they can return to an unfinished decision without reconstructing it. Existing Web Analytics and aggregate `/go` reports cannot attribute return visits or conversions specifically to notes. Review that qualitative feedback and owner-provided aggregate traffic before expanding. No note contents should be collected for measurement.
